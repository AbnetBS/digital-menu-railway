# Merge and rollout audit — 28 October 2026

## Verdict

**Not yet cleared for production.** The automated suite, TypeScript check and production build pass, and isolated PostgreSQL-compatible/HTTP tests exercised key Store, payroll and authorization flows. They do not prove the upgraded app works on the existing VPSDime/Coolify installation, on real PostgreSQL under concurrency, or on the physical scanner. The code and documentation changes in this branch are not deployed or merged.

## Conditions to satisfy before production

1. **Backup and staging:** take and verify a restorable PostgreSQL backup. Test the exact candidate on a restored copy using the actual PostgreSQL version and application permissions. The new payroll and Store schema migrations run against persistent data; rolling code back does not undo data or DDL. Confirm correct legacy breakage migration, frozen/paid payroll, and backups before and after the change.
2. **Real concurrency:** exercise simultaneous Store issues, station purchases and waste, repeated Done/print/delivery, and payment versus breakage on real PostgreSQL. The embedded tests are not a concurrency test. Verify trigger creation and schema ownership with the actual database user.
3. **Firmware and Wi-Fi:** compile and flash the production sketch separately, with the real board and installed Arduino core/libraries. At the door, unplug/restart Wi-Fi and separately interrupt only internet, scan while offline, restore connectivity, and reconcile times/order/results. Check the 20-column LCD signal line and a weak signal. Test startup without Wi-Fi, enrollment, sensor, filesystem-full and power-recovery behavior. No physical device or toolchain was available in this audit.
4. **Offline attendance risk:** the queue now retains non-200 responses in order and avoids automatic filesystem formatting, but it still has no transactional exactly-once acknowledgment. A lost response or power loss after server commit can cause a retry; a corrupt/unresolvable first entry can block later entries, and storage is finite. The queue keeps remaining entries in memory during rewrite. Reconcile attendance after outages and monitor the device serial logs. Scans made after a reboot but before the first successful NTP sync, or arriving more than three days late, use arrival time. The 10-minute Wi-Fi watchdog restart can cause such a reboot. An audited deduplication/recovery mechanism and durable clock would be needed for stronger guarantees.
5. **Device security:** set a strong `ATTENDANCE_DEVICE_TOKEN` consistently on the scanner and server with a coordinated rollout; otherwise the legacy default leaves device endpoints open. The updated endpoints enforce the token when configured. The sketch does not explicitly configure a trusted TLS CA; establish how the installed ESP32 Arduino core validates the site's HTTPS certificate before sending a device secret on an untrusted network. Change the known first-setup hotspot password locally, and never commit device secrets. Rotating a server token without flashing devices will prevent scans from syncing.
6. **Live Coolify configuration:** verify the actual `DATABASE_URL`, `SESSION_SECRET`, `ADMIN_PASSWORD` and `NEXT_PUBLIC_SITE_URL` (the latter at build and runtime), DNS/HTTPS, trusted proxy headers, SSE, clock/NTP, storage, backups and logs. Keep one app process/replica because real-time pub/sub and rate limits are in memory. If old receipt cleanup is desired, set up and test its separately authenticated Coolify schedule; it is not automatically scheduled by this app.
7. **Operational acceptance:** enter and verify recipes and main/station opening stock, open `/store` so the trigger is installed, and physically count items before trusting estimated balances. Completed historical lines are not backfilled. A later edit, removal, or cancellation of an already-Done line does not reverse/recalculate usage. There is no audited physical stock reconciliation. Review payroll deductions and approvals with the appropriate authorization. Test representative cashier, waiter, station, sales reports, payroll print and notification workflows on staging and verify local staff access.
8. **Lint gate:** full `npm run lint` failed on the existing repository with 34 errors and 43 warnings in the audit run; targeted lint for the newly changed Store/security paths passed. Decide whether a clean full lint is required by your merge policy. These results are not a guarantee that every changed file is lint-clean.

## Findings addressed in this branch

- Replaced deployment-facing references and guide with VPSDime/Coolify/PostgreSQL, named the npm package `fana-cafe`, and made the public canonical URL explicit. The GitHub repository and fixed Arena branch were not renamed.
- The configured attendance token now guards fingerprint clock submissions and device mapping/pending-job reads, not just offline timestamps and some writes. The PIN/supervisor path is unchanged. With the token unset, the previous compatibility behavior remains open.
- Corrected Coolify receipt-cleanup bearer parsing and made cleanup failures propagate rather than report a misleading zero.
- Kept Wi-Fi credentials on recovery, gave slow routers 30 seconds between radio resets, retained ordered offline failures, warned on failed queue writes, and avoided auto-formatting LittleFS. The existing LCD displays `Connected`, the numeric dBm value and bars; this is Wi-Fi signal strength, **not** a test of internet reachability.
- Updated Next.js and matching lint config from 16.2.6 to 16.4.3 after the registry reported critical advisories. `npm audit --omit=dev` reported zero vulnerabilities after the update. Full `npm audit` still reports four **moderate development-dependency findings** through `drizzle-kit` / its esbuild loader; the suggested automatic fix is a breaking downgrade. Do not expose a vulnerable development server to untrusted networks. Audit results can change as advisories are published.

## Tests actually performed

- `npm test`, `npx tsc --noEmit`, `npm run build`, targeted ESLint and `git diff --check` passed after the core changes. Full lint did not pass as noted above.
- With a disposable embedded PostgreSQL-compatible database and local HTTP app, the audit checked device token rejection/acceptance for clock, mappings and enrollment polls, and cleanup bearer rejection/acceptance. Earlier isolated HTTP tests covered direct imports, request destination and acceptance, station Done/waste, payroll breakage and paid lock, and Buna delivery/print once-only deduction. Temporary test services were stopped and did not touch production.
- Wi-Fi and queue regression checks inspect firmware source; they do not compile or execute the ESP32 firmware. No real VPS, PostgreSQL concurrency, physical scanner, browser/point-of-sale acceptance, or production deployment was tested here.
